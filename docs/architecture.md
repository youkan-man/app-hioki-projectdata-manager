# 簡易設計

## 構成

| ID | 要件 | 設計判断 |
| --- | --- | --- |
| D-001 | RQ-001–RQ-004 | React/Vite の SPA を nginx から配信し、`/api` を FastAPI にリバースプロキシする。 |
| D-002 | RQ-005–RQ-009 | Chromium の File System Access API で許可済みディレクトリを走査・復元する。ZIPはプロジェクトフォルダーの中身だけを直下に持ち、復元時にUUIDフォルダーを1回だけ作る。 |
| D-003 | RQ-008、RQ-010、RQ-011 | PostgreSQL をプロジェクト/バージョン/論理削除の索引、ZIP を不変の実体として扱う。 |
| D-004 | RQ-012 | backend には `/data/archives` だけを公開し、保存実装からホスト側の named volume/bind mount の違いを隠す。 |
| D-005 | RQ-013、RQ-014 | HTTP は `0.0.0.0:8080`、任意 HTTPS は `0.0.0.0:8443`。`.env`の`PUBLIC_IP`を証明書CN/IP SANの正とし、公開アドレスとポートは環境変数で変更する。 |
| D-006 | RQ-015 | UUID/拡張子/ZIP 内容を検証し、展開前に絶対パス・`..`・シンボリックリンク等を拒否する。 |
| D-007 | RQ-016 | 指定バージョンのflat ZIPを一時処理し、ZIP直下の単一 `*.gprj` と `layout.lay` をJSONとして編集する。他entryは元payload bytesをそのまま新ZIPへ複製し、既存の保存処理を通して連番の新版を作る。 |

## 実行時データフロー

1. ブラウザーは初回に利用者が選んだ GENNECT Space データディレクトリのハンドルを IndexedDB に保存します。
2. 登録モーダルを開くと権限を再確認し、UUID 子ディレクトリ内の `*.gprj` を検索します。
3. 選択したUUIDプロジェクトフォルダーの中身だけをブラウザーで ZIP 化し、`/api` へ登録します。直接 ZIP アップロードも同じ検証経路を通します。
4. backend はflat ZIPを `/data/archives` に不変オブジェクトとして保存し、PostgreSQL にプロジェクトとバージョン索引を追加します。UUIDが1階層だけ付いた旧ZIP入力は、ラッパーを除去してから保存します。
5. 復元時はブラウザーがflat ZIPを取得し、対象 UUID フォルダーを1回だけ作って、その中へ安全に展開します。既存なら確認後に置換し、二重UUIDディレクトリは作りません。
6. 削除は DB の削除日時を更新するだけで、ZIP は保持します。
7. JSON編集時は対象バージョンを読み、root-level `*.gprj` と `layout.lay` の指定箇所だけを変更します。元バージョンは残し、編集済みZIPを同じプロジェクトの次バージョンとして追加します。

## 永続化境界

- `postgres_data`: PostgreSQL のデータディレクトリ。
- `project_archives`: 既定の ZIP 保存先。backend には `/data/archives` として見えます。
- `compose.storage.example.yaml`: `/data/archives` をホストの絶対パスへ差し替える例です。アプリ側コードは変更しません。
- アーカイブキーは `<プロジェクトUUID>/<8桁バージョン番号>-<SHA-256>.zip` とし、プロジェクト名は ZIP 内の `*.gprj` から再取得します。これだけを使って最低限のプロジェクト/バージョン索引を再構築できます。

## 運用・セキュリティ境界

- 認証・利用者別 ACL は設けず、到達できる全利用者に同じデータを表示します。必要なら LAN/VPN/ファイアウォールで到達範囲を絞ります。
- TLS 終端は nginx です。自己署名証明書は動作確認用とし、共有運用では社内 CA 証明書を推奨します。
- PostgreSQL と backend はホストへポート公開しません。外部入口は nginx のみです。
- ZIP の MIME/拡張子だけを信用せず、展開後パスと総容量を検証します。
- 受理するレイアウトはflat形式と、入力互換用のUUIDラッパー1階層だけです。ラッパー内のラッパー、複数root、root直下に `*.gprj` がないZIPは拒否します。

## プロジェクトJSON編集境界

- 編集対象はZIP直下に1つだけ存在する `*.gprj` と、ZIP直下の `layout.lay` です。どちらかがUTF-8 JSONとして解析できない場合は新版を作らずエラーにします。
- 利用者が指定したJSON値以外の論理内容を保持します。JSONの再シリアライズによって `*.gprj` と `layout.lay` 自体のbytesは変わり得ます。
- `*.set`、画像、計測データ、未知拡張子、サブディレクトリ内ファイルは編集対象外です。名前が `layout.lay` ではない `.lay` も編集対象に含めません。
- 編集対象外entryはentry pathと展開後payload bytesが元ZIPと一致しなければなりません。ZIPコンテナの圧縮方式、entry順序、時刻などのメタデータ同一性は要求しません。
- 新版作成は通常のバージョン登録と同じ連番・不変保存を使い、元バージョンのZIP、SHA-256、メモを変更しません。2 JSONの変更は1つの新版へまとめて原子的に保存し、片方だけ更新された版を作りません。
